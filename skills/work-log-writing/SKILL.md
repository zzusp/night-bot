# 工作日志写作

面向阅读者总结当天的工作结果。本技能提供取材和表达方法，不改变业务授权、验收标准或次日排期。

## 使用

- 使用模型工具 `skill` 加载 `work-log-writing`；已认证用户可用 `/skill:work-log-writing` 显式选择。
- 首次使用先读 [工作日志示例](references/example.md)。相对路径以工具返回的 `resourceBase.path` 为基准。
- 示例已经脱敏，仅用于学习组织和表达，不作为实际任务、部署、验收或授权的证据。
- 只使用当前会话有权读取的材料。编写日志不授权修改业务状态、部署、发消息或新增次日承诺。

## 取材和归并

1. 先确认日期、时区和截至时间，读当天的任务结果及相关反馈。同一事项的创建、修复、部署、复测、补修合成一条，写清截至汇总时推进到了哪一步。
2. 后续纠正、范围调整和新结果要更新旧结论。明确免除的复测不再列成任务阻塞；已经恢复的环境不再写成待恢复。不同时间的状态不能并排堆放，交给读者自行判断。
3. 区分 Bot 实际做的事与他人完成的操作或反馈：确认环境已恢复，不等于 Bot 恢复了环境；反馈方验收通过，不等于 Bot 亲自完成现场验收。
4. 状态用业务语言准确表述：已修复、已部署、反馈方已验收、排查有结论但尚未修复。任务系统的“完成”“等待”不能直接替代这些判断。
5. 尚未解决的事项写具体缺口及下一步；建议跟进与已承诺明日完成分开。当天没有次日排期就省略空栏目。

## 表达

- 开头用一句话交代当天主要成果，然后按业务事项写结果、关键原因和当前状态。
- 每件事保留影响理解的技术细节。例如“数值按字符串写入导致保存失败”比堆字段类型、请求码和构建编号更容易判断进展。
- 不把收到多少消息、模型响应多少次、创建多少事项当作工作成果。不逐条复述聊天，不在正文重复贴任务记录。
- 内部作业 ID、授权修订号、错误码、完整哈希和大段证据索引留在原始材料；影响交付的内部异常用一句话说明其具体影响。
- 验收范围和不确定性放在对应事项中说一次。必要的“未现场验证”须保留，不把整份日志写成重复免责声明。
- 有实际沟通或执行教训时，写明哪次行为需要改进及下次动作，不用空泛的“提升效率”“加强协作”。
- 保留可核对的来源入口，正文面向阅读；不为日报重跑测试、追查无关历史或创建额外审查流程。
- 真实日志与证据保存在私有运行数据中，不将客户信息、账号、内网地址、原始聊天或业务附件写入仓库示例。

## 生效边界

本技能供支持技能发现和调用的 Bot 会话按需参考。当前定时工作日志使用独立、无工具的固定提示请求，不加载本技能；安装或引用本技能不代表定时日志已采用示例。不要宣称已完成模型训练、自动采纳或新日报效果验收。
