# 执行记录提交暂态与读取成本

## 已确认问题

运行中的任务页收到 HTTP 200、`status:pending,reason:SESSION_COMMIT_PENDING` 后，前端将其变为合成的 503 错误。旧记录被保留，但聚合提示变成“读取内容暂未更新”。真实浏览器复现后约6.4秒自行恢复；这是提交窗口，不是已证实的 HTTP 5xx 或日志损坏。

另有慢读：约21.5MB日志的 live 请求最高19.526秒，接近20秒客户端期限。每个 live 请求以64KiB逐块异步读取完整日志；它与业务处理共用事件循环，很多短读的续执行被排队。活跃客户端最快每250ms发起下一次读取，历史约2.5秒核对一次。

## 方案比较

1. 只延长超时或保留错误提示：不能纠正正常提交状态，也不减少反复读取成本，不采用。
2. 仅以 mtime/size 或过期缓存放行 live proof：无法核验当前真实字节及文件替换，削弱既有安全合同，不采用。
3. 独立展示提交暂态；通过原打开文件句柄读取完整字节、计算相同摘要，保留前后身份检查；活跃 live 读取间隔改为1秒。采用，不增加服务、缓存协议或展示专用核心字段。

## 行为与边界

- 已有获权快照时，提交暂态保留历史、TODO与已提交用量，更新时间不前移；清除临时输出及旧 live proof，显示局部“记录正在提交”，继续核对历史。
- 首次提交等待与执行未开始继续分别展示。真实网络错误、不可读、身份错误、撤权及前缀变化仍走既有失败关闭/重取流程。提交等待不能清除这些错误后再展示未经新授权的旧记录。
- 每次摘要读取仍读当前字节，不复用完成的校验结果；仅合并并发读取。保留受控路径、symlink/hardlink、inode、size、mtime、ctime及当前路由前后核对，读入长度必须等于打开时长度。严格提交链与可移植解码路径不改。
- 1秒 live 轮询仍串行；历史补读、页面隐藏取消及三次真实错误后的停止规则不变。不增加生产重试或业务调度。

## 最小验证

- 真实浏览器覆盖旧快照→连续提交等待→追加成功、首次提交等待、提交后真实错误/撤权；旧消息不重复，更新时间及展开状态不被伪更新。
- 大文件摘要与独立当前字节hash一致；同长改写/还原mtime、替换inode、读取中变更、symlink和并发读取守卫继续有效。
- Web相关单元/浏览器测试、类型检查与构建、原生源码守卫。只读对照实际日志的摘要成本；不复制业务数据、不制造真实失败或发消息。
- 合并前不替换正在执行的生产实例；部署只用已合并发行，保留既有安装数据。
