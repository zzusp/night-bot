# Router 正常停止批次续办

## 现场与根因

原任务的 PowerShell 调用有真实原生作业 `killed` 终态，无成功效果收据；未知效果保护正确，不能改成成功。操作者实际核验原命令、已提交日志及真实排空后，通过现有 effects 入口按可能部分效果结清，原调用保持 noReplay。

同一会话另有 `ROUTER_BATCH_UNSETTLED`：原 Router 已接纳批次，最后 assistant 为正常 `stop`，没有结清事件。默认恢复有意不重放 admitted 输入；正式 inspect/resume 入口又只接受 error/aborted 检查点，导致这个状态没有受控恢复路径。

## 方案比较

1. 直接 consume inbox、改 SQLite 或重新投递原输入：丢失必要动作证明或重复业务，不采用。
2. 正常 stop 后自动无限续轮或只增强提示词：前者可重复外部动作，后者无法修复已存在检查点，不采用。
3. 复用受信操作者显式续办，允许正常 stop 检查点；原生历史/当前身份/完整 inbox/当前权限/工具与作业终态/单次领取校验全部保留。采用，不新增模型会话、调度器或通用重试。

## 改动边界

- 仅将当前分支最后 assistant 的 `stop` 纳入已有显式检查点资格；仍须原批次 admitted、来源合法且无新输入绕过。
- 工具调用必须完整配对且结果非错误，未结作业和效果仍拒绝。不会把正常 stop 内的未配对调用视为未派发。
- 默认冷恢复仍仅自动续接符合既有条件的 aborted，正常 stop 必须操作者 inspect/check/resume；每个检查点只能领取一次。
- 保留原 generation/session、物理提交、历史前缀和原业务输入/admission唯一。模型统筹后续真实输入，完成必要动作后自行 settle。
- 私有现场证据仅留安装 data，代码提交不含身份、调用参数、路径、消息或业务产物。

## 验证与发布

复用默认 Host/Pi、本地模型、假渠道的原批次续办回归，新增正常 stop 的冷恢复、CLI inspect/check/resume、并发/陈旧拒绝、当前memory admission、原历史前缀与输入唯一、结清及二次冷恢复不重放。原 error/aborted、工具失败与未知作业拒绝边界继续验证。

先合并再部署，同步核心与Web插件。未知效果按原正式入口处理，不重新执行历史脚本，不访问或修改外部业务系统；已合并页面修复一起上线。正常IPC关闭应等待真实执行者排空，持久pending事件本身不等于活跃工具，升级不能以清除pending制造停机条件。

## 续办结清上下文补充（2026-11-16）

上述入口部署后原事件已消费、原任务完成，但新完成事件的模型轮只查询来源并返回文字，没有调用settle；显式续办同样未结。原控制消息仅泛称“未结事件”，准确事件引用需从长历史定位，且没有直接说明本轮结束前必须调用的工具。学习维护失败也不能抹掉完成交付。

比较三种处理：反复领取新检查点不能修复缺失上下文；Host直接consume绕过模型结果评估；在原受控续办消息内提供已通过守卫的原packet及supplements事件ID全集，并明确resident_router_settle义务。采用第三种，不添加自动重试、不修改settle前置条件或学习来源守卫。

边界验证使用真实Host发往本地模型的请求，核对检查点事件集合覆盖原输入与较新取消、没有把控制消息转成来源；原严格CLI/冷恢复/并发拒绝保持。脚本模型测试只证明上下文传递和生命周期，现场模型能否实际结清须部署后独立验收，不以提示词出现冒充解决。
