# 执行历史读取延迟

## 目标和证据

修复 Web 历史轮询拖慢同进程轻接口的问题；完成本地实跑、PR 合并和本地部署。已有同数据对照：18.6 MB 任务日志严格读取 1302ms，11.6 MB Router 日志 673ms；Web 投影分别约 104ms / 37ms。无增量任务轮询仍耗时 1416ms，期间 health 达 1173ms。新版跨块脱敏仅增加十几毫秒，不能解释线上秒级排队。

## 决策

1. 在 readNative 复用已严格验证的完整快照。每次仍检查路径并读取实际字节，按路径、codec 身份和 Buffer.equals 判断；不使用 mtime、size 或最后 entry ID 代替完整性证据。返回独立副本。按原字节总量限制 LRU（32 MiB），关闭时清空；不缓存未提交尾。
2. live 投影复用精确 pending call 绑定，只投影临时增量，不再二次脱敏全部历史。保留重复 ID 歧义、公开结果 schema 和跨块脱敏。
3. 不改轮询频率和 UI 合同，不修改推理/业务执行、writer、离线严格解码和未知作业防重放。

## 比较

- 仅调慢轮询：不解决单次秒级同步工作，不采用。
- 仅以文件 stat 或 commit ID 缓存：无法检测同大小改写和物理尾，不采用。
- 字节一致的已验证快照缓存：仍读取当前物理证据，减少重复解析和 Pi 上下文构造，采用。暂不增加 Web 脱敏缓存，避免秘密轮换失效和第二套 revision 机制。

## 验证

真实 journal 覆盖重复读取、调用方修改隔离、新提交、同大小/mtime 篡改、未提交尾、路径变化和取消；复用现有秘密轮换、Router 身份和 live 工具配对测试。使用只读真实大日志对照和实际 HTTP 历史/轻接口并发测量；不复制业务数据入库。结果集中记录验收报告，部署仅基于已合并 SHA。
