# 反馈取证与提交正文

已核对的长任务有 1,017 条工具结果，原诊断工具只允许浏览前 185 条，并忽略已提交会话中的 Skill 读取回执。能证明取证盲点，不能据此确认技能加载异常的原因。

仅提高页码上限仍会要求模型逐页找异常；直接开放原日志、技能正文或全量会话会扩大权限。沿用已授权的会话证据接口，增加异常和技能两种聚焦视图，按原有配对和归属核验返回固定字段，不公开名称、路径、原文、版本值。读取成功、受信回执、异常与缺证据分别表述。原先完整的证据附录留在同一会话的预览里，GitHub 默认正文使用自包含的现象、关键证据和未核实事项；用户原描述和单独确认仍保留。

使用合成长会话复验后段异常和可信 Skill 回执；验证报告预算、证据折叠以及 GitHub 请求只包含实际预览正文。原任务只做只读核对，不重跑、不提交 Issue、不部署。

## 续修：识别两次读取前仍可见的同一提示

在线复验只定位到重复调用。原会话两批调用前的 Pi 原生投影显示：同一压缩检查点的系统节一直点名相关 Skill，上一批成功结果也还在。旧取证只数历史中的 `night.skill-version-notice`，无法区分「未收到新提醒」和「上下文中仍有旧提示」。

只看提醒时序无法补齐这个缺口；直接给诊断模型看系统提示、压缩摘要或私有会话正文又超出取证范围。对首屏代表性重复和分页中的复读，使用 Pi 官方投影分别读取两次调用之前的已提交上下文。只匹配产品自己的刷新系统节或原生提醒的已知格式，在本地关联匿名 Skill；向模型提供同一提示的来源、时间、原因类型和上一成功结果是否仍在，不输出提示、指令或推理原文，也不把上下文等同于实际发给厂商的请求。验证压缩检查点、后来相同文本但不同记录、上下文删掉成功结果及无提示的反例；不调整刷新逻辑或重放原任务。
