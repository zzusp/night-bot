# Router 只读查询并行与排队

UAT 已观察到 `resident_task_lookup_async` 可按原会话回流；一次查询子推理约 4 秒、网页首答约 49 秒。单次样本不能证明 Router 排队是这 49 秒的原因。代码中另外确认：第二条同会话请求及第三条全局请求被 `ROUTER_LOOKUP_CAPACITY` 拒绝，导致突发进度追问无法充分走已有分流工具。

仅改现有只读查询：保持全局两个实际执行位，允许同会话的不同来源占用；第三条起先写原 SQLite 账本，再按接纳顺序等待，不压住 Router。继续使用接纳时起算的 30 秒截止时间，超期不启动。一次来源版本对应一个查询，重复用原操作回执。结果仅回原 Router；重启将无法确认仍在本进程执行的记录结为中断，不自动重跑。无新通用子代理、数据结构、写权限或执行会话。

单纯改提示词不能消除硬拒绝；只提高全局并发会把峰值转移到模型服务；复用持久接纳并限制实际推理能同时保留削峰和快速交接。验证同会话两条同时推理、第三条耐久排队且释放后实际回流，同时保留过期、已撤回来源、关闭和恢复边界。
