# 文件编辑失败的效果边界

## 目标与现场证据

修复单任务执行将 Pi 文件编辑的写入前错误误判为未知外部效果的问题。只读复现确认：待替换文本在保留脚本中出现两次，Pi 1.5.0 在唯一匹配检查时拒绝编辑，未调用写入。当前任务效果中间件把所有 `isError` 都升级为 `TASK_EFFECT_UNCERTAIN_NO_REPLAY`，并覆盖原错误。

## 方案取舍

1. 按错误文案或工具名放行：拒绝。自定义同名工具可以已经写入，错误文本不能证明无效果。
2. 成功后才记录效果意图：拒绝。丢失进程中断后的防重放保护。
3. 由受信的 Pi 文件适配器记录真实写入边界：采用。每个已注册执行用私有身份绑定状态，在调用 `fs.writeText` 前标记开始，等实际执行排空后才可证明未开始写入；精确工具定义及执行身份必须匹配。

## 实施边界

- 保留执行前提交的原效果意图、调用身份去重、权限和版本检查。
- 仅对精确注册的 `write` / `edit`，在执行已结束、从未进入文件写入且未取消时，提交 `effect-result` 的 `isError: true, effect: not-started`。原 Pi 错误返回模型，允许读取后发起独立修正调用。
- 冷启动认可这类失败终态，但不重放原调用，也不伪造成功。旧版只有 `isError: true` 的结果仍是未知。
- 已进入文件写入、写后回执丢失、自定义工具、取消和未知后台作业继续保持原未知效果保护。
- 对账检查必须识别已结清的未开始写入结果，拒绝再次对账。
- 不修改线上数据库或历史 journal，不借此次平台修复重新发布外部业务。历史旧版已丢失原始错误，不能因新逻辑而自动补造无效果证明或解除旧任务。

## 验证

用真实 Host / Pi 文件能力复现多匹配编辑失败，核对原文件不变、原错误回传、唯一匹配修正成功；冷启动后显式续办同一任务并核对失败与成功收据。用真实文件写入后抛错验证未知效果仍被保留，并验证同名替换/伪造执行不能获取未写入证明。运行相关文件工具、单任务、对账与调用身份回归及源码/导入检查。运行结果归入 `docs/acceptance/task-file-mutation-outcomes/`，不覆盖其他会话结果。

## 2026-11-13：底层准入与后续核验排空补齐

### 新证据

PR #33 已在主线和本机正式发行中，但 `fs.writeText` 内仍先执行原子锁内的观察/版本校验。适配器在进入该方法前标记开始，无法区分尚未进入 `_publish` 的拒绝。现场同名文件先由命令生成、后由未读文件工具覆盖，旧错误仅保留未知效果码；新实现不得补造旧结果。

旧 owner 的真实排空证明后又有数轮只读核验，严格读者因此拒绝过期切点；后续核验租约没有自己的排空凭据，当前代码只为同租约未知意图产生凭据。

### 方案取舍

1. 按 `FS_NOT_OBSERVED` 等文案/字段放行：拒绝，写后抛出的同名错误不能证明无效果。
2. Pi 适配器先 stat 后再写：拒绝，重复底层准入且无法覆盖锁内版本竞争。
3. 底层写入方法记录真实准入拒绝的私有证明：采用。绑定实际文件系统及实际失败对象，仅在进入任何发布/目录/暂存写入前产生；适配器仍以已结束的精确执行交付证明。进入 `_publish`、取消或响应丢失继续保守保持未知。

后续核验 owner 在真实排空后产生自身绑定的证明；检查时必须同时找到目标调用原 owner 的有效排空及最终 owner 的新切点，不把后者当旧调用原 owner 的证明。最后切点后仍只允许物理 commit 标记，活 owner、未知作业、跨作用域、缺原始证明和分支篡改继续拒绝。

### 交付范围

仅修工具/恢复责任层和必要回归、文档。旧任务经操作者确认可能部分效果结清后，在原目标授权下续办；不恢复已退役的全任务新增授权门槛，不重放旧调用或直接修改历史。
