# 第四轮：完整重启计时

## 范围与源码

用户明确要求再正常重启一次，记录完整耗时。本轮不改代码、配置、依赖或发布版本，不发送测试消息，不重放业务。实际版本仍为 `585e1c767ee7d45b6422ff43e5d288489c06f697`，发布检出 tracked 工作树干净。第三轮的实现/测试结果保留；本轮只验证真实停启与就绪计时。

本轮完整计时和关键结果保留于下文；JSON 附件在第五轮证据核实后清理，最新证据见[第五轮](round-5.md)。矩阵见 [matrix.csv](matrix.csv)。

## 计时方法

- 停机前完成版本、配置、原实例存活、凭据可用性及认证渠道就绪的零副作用 `--check`，准备时间不计入重启。
- 同一计时进程用 `performance.now()` 连续计时；起点紧邻向现有监督器发送正常 IPC 停机请求。
- 等旧 supervisor、launcher、worker 全退出，且安装锁及原元数据释放，记录停机耗时，再立即启动同一版本。中间不经过人工操作，不重置计时。
- 250 ms 间隔检查（单 HTTP 请求超时 2 秒）。终点为 Web 和 resident HTTP 均 200，且认证 `/api/channels` 回读原两个启用渠道均 connected、listening、无错误码、无需重启。不是仅以进程存在或端口可用作为完成。
- 下列数值是首次成功观察的耗时，包含探测开销；以单调时钟为准，墙钟时间供追溯。

## 实际结果

本机时间：2026-11-10 **15:40:27.279 +08:00** 发出停机请求，**15:44:46.942 +08:00** 确认全部就绪。

| 指标 | 耗时 | 口径 |
| --- | ---: | --- |
| 正常停机 | 0.443 秒 | 请求至旧进程全退出、所有权释放 |
| Web 可用 | 255.940 秒 | 从停机请求起算 |
| resident HTTP 可用 | 255.963 秒 | 从停机请求起算 |

仅执行一次正常重启，forced=false，无 kill、手工删锁、暂停计时或绕过恢复检查。配置哈希不变，两个真实钉钉渠道均 listening/connected、运行错误码为空。服务保持运行；本轮不再重启。

原 `/health` degraded、recoveryIssueCount=1 告警保留，没有自动清除或续办外部效果。未重复第三轮逐记录持久性校验、16 项相关测试或全套 runtime/routing/containment，不将历史通过记作本轮实跑。

## 结论与边界

完整重启仍需约 4 分 20 秒，耗时主要在新进程端口开放之前的启动阶段；先前的修复解决了普通停机全量封存，不能据此宣称完整重启已提速。本轮未定位启动内部具体慢点，也未修改启动逻辑。
