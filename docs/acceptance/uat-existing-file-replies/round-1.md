## 判定

- 旧版只能按已冻结的 `artifactIds` 发回任务文件；原件如果只登记了 `work/` 路径，后续无法用既有交付路径选择。旧执行端还以固定句式及显式路径判定入库意图；普通上下文指代不能通过该入口。这两个代码缺口已在本地验证修复后的路径。未确认现场入库请求命中的精确拒绝码。
- `node --test test/pi-router-attachment-capability.test.js`：最终 3 项通过。原通知仍保持正文与附件独立回执、缺能力时不假报送达。新请求在原会话发回未冻结原件，查验原字节；重复请求事件未多发，错会话、错版本和越界选择均未产生目标副作用。原任务未重开、未改完成记录。知识库验证原件及条目，第二渠道按相同 ID、版本和 SHA-256 读回原字节。关闭 Host 后经 `backupTask` 和 `validateTaskArchive` 正式封存，查验冻结原件 SHA-256 和独立请求源；篡改源作者并重算账本摘要仍被拒绝。
- 指定 `cortex-cowork` 经实际 Router 和假渠道发送：脚本执行模型先创建已完成且排空、只报告未冻结的原件，然后真实 Router 处理两条自然话请求，产生一次已读回的私聊附件并验证入库。入库文件 SHA-256 与附件一致，原完成记录不变。另用真实 Router 验证三条回复：只问在册数不列排除项；入库失败只给结果和原因；明确问注销数则回答。第二渠道读回由脚本模型经真实 Host 验证，未作真模型或厂商端宣称。
- DWS 文本、文件适配、原生发送、任务交付、单任务档案和共享资源 6 个定向套件：79 通过、1 跳过（Windows 文件软链接权限）。适配器仅变更新单行短答的简单行内代码投影，保留结构化 Markdown 和原有字面文本。历史厂商接口可见富文本转换，但所核对的冻结正文和对应回读没有相邻重复，尚不能确认重复出现在哪一层；钉钉客户端未验。
- `pnpm check` 与 `git diff --check` 通过；480 个运行时 JS、0 外部 SDK 导入，源码来源、哈希与原生边界检查通过。

## 排障与复验

- 最初将旧能力场景、两次重启和新文件全链塞进同一个 130 秒测试，在 `send-reported` 阶段超时，未到封存。独立拆为两个保留全部断言的场景后，旧能力用例 101.2 秒，新用例 80.2 秒，均在原期限内通过。未放宽生产或测试预算。
- Router 广回归首跑 53 项，51 通过、1 失败、1 超时；失败项在主线提交 `7b400e48` 改提示措辞后仍要求旧句。改为验证当前的会话内调度与副作用边界，单独复跑通过，实际暂停、取消、恢复、重开与归档再激活仍沿原执行会话。超时项由上面的拆分复验覆盖，不把首次广回归记成全绿。
- 真模型包办从原件生成到第二渠道读取的尝试未通过，关闭时报告 `TASK_SESSION_DRAIN_FAILED`，未确认发生于业务请求的哪一步。替代复验隔离了种子生成与 Router，验证了本次改动所负责的真实选路与副作用，但没有验证真模型生成原件与第二渠道的完整串联。
